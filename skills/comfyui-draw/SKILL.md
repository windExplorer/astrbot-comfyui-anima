# ComfyUI 绘图技能（astrbot_plugin_comfyui_anima）

你拥有 ComfyUI 绘图能力，**唯一的出图方式是调用插件提供的 LLM 工具**。口头说"我会画""马上"不等于画了图。

## 你能做什么

通过调用插件提供的 LLM 工具出图：

- `comfyui_draw`：文生图 / 附带参考图时自动图生图。核心参数 `prompt`（单张），或多条画面用 `prompts`。
- `comfyui_img2img`：基于一张参考图做变换 / 重绘。`prompt` 传"变换意图"（单张），或多个变换用 `prompts`。
- `comfyui_loras`：查询当前已配置的 LoRA 库（名称、关键字、底模、描述、触发词）。需要用户提到"用某个 LoRA / 某风格画"但你不确定可用列表时调用。
- `comfyui_workflows`：查询当前已配置的工作流列表（名称、是否支持图生图、是否 Anima）。
- `comfyui_gallery`：发**以前画过/收藏**的旧图（不属于"画新图"，不要用它替代出图）。

> 工具调用顺序：**comfyui_draw 永远是真出图的最终一步**。comfyui_loras / comfyui_workflows 只在"需要确认可用项"时作为前置查询，不是必做的前置流程——拿不准就直接不传 workflow/loras，让插件用默认，照样出图。

## 铁律 0：只要用户要【新】图，就必须真调 comfyui_draw，禁止只说不动

这是本技能最重要的一条。**用户说"画/生成/来张图/给我弄个图/换一张/再来一张/怎么还不出图"等任何要图意图时，必须调用 comfyui_draw（或 img2img）并真正等待出图结果。** 以下行为都是错误的：

- ❌ 只回复"好呀~这就给你画""马上动手✨""在跑图了，再等几秒"而不调用工具——这等于没画。
- ❌ 第一次调用出图失败/超时后，只回"我再试试"而不重新调用。
- ❌ 因为对话记忆里"画过了/之前说过要画"就不再调用。
- 用户催"图呢/卡住啦/怎么没看到图"时，**更要立即调用工具**（而不是解释）。

只要用户想要的是**新图**，无论多隐晦、无论对话聊了多久，都要真调工具。

## 强制出图标记（消息以 `t` 开头 = 必须画出来）

用户可能给消息开头加一个**强制出图标记**（插件默认前缀是 `t`，管理员可改）：

- `t发张照片`、`t 一个女孩`、`t 猫耳少女站在雨里`、`t把这张图变成水彩`（带参考图 → 图生图）
- 看到这个标记时的正确做法：**把标记去掉**，剩下的内容作为画面描述，**立即调用** `comfyui_draw`
  （或带图时 `comfyui_img2img`）。这条消息的语义就是「必须画出来」。
- ❌ 只回复「好的，马上画」而不调用工具 = 失败：插件会在本轮结束时**替你补画**（用去掉标记的原话），
  但你的理解更准、参数（工作流 / LoRA / 尺寸 / 多张）也更合适，所以**优先你自己画**。
- ⚠️ 别误判：标记必须在**行首**，并且后面紧跟的**不能是英文字母** —— `thanks`、`the cat is cute`
  这类普通英文句子**不是**标记，也不是画面内容，照常按聊天处理。
- 标记后面没有内容（只发了个 `t`）→ 按普通对话询问用户想画什么。
- 标记只表示「必须画」，**不改变其它规则**：数量、多人分组、角色保真、禁语法、按底模选写法全都照旧。

## 数量规则：一次调用出完，绝不拆成多次

**★ 铁律：一条用户请求只调用一次 comfyui_draw（或 comfyui_img2img）。**

要几张、几个画面，全部用参数在这一次调用里说清楚。插件对同一条用户消息有硬性出图闸门：
本轮已经出过图之后再调用，会被直接拦回、**一张新图都不会产生**，纯粹白费一轮。

两个参数（都在同一次调用里传）：

- `prompts`：**多个不同画面**，数组，**要几张就传几条**，每条各出 1 张。张数 = 本数组的条数。
- `count`：**当前恒为 1，一般不用传**。本参数是预留给将来"同一提示词跑不同种子出多张"用的；
  现在传大于 1 会被插件拦回并要求改用 `prompts` 数组。

| 用户怎么说 | 怎么传（一次调用内） |
| --- | --- |
| 没提数量（"画只猫"） | 用 `prompt` 单条即可，不传 count |
| "来 3 张猫" | `prompts=["姿势A的猫…", "姿势B的猫…", "姿势C的猫…"]`（3 条不同画面，每条 1 张） |
| "来几张 / 多画几张"（没给具体数字） | 按 3 张处理，`prompts` 传 3 条不同画面 |
| "画猫、狗、兔子" | `prompts=["猫…", "狗…", "兔子…"]` |
| "白天、晚上、深夜" | `prompts=["白天…", "晚上…", "深夜…"]` |
| **"白天、晚上、深夜各来 2 张"** | `prompts` 传 **6 条**（白天 2 条 + 晚上 2 条 + 深夜 2 条），每条各 1 张 = 6 张 |

**"各来 X 张"= 每组拆成 X 条、总条数 = 组数 × X**：把每个具体画面都写成 `prompts` 的一项。
例如"白天、晚上、深夜各来两张" → 白天 2 条 + 晚上 2 条 + 深夜 2 条 = 6 条，每条出 1 张 = 6 张。
**不要用「单条 prompt + count=N」**——那只会出同一个画面的 N 个近似副本，用户要的是 N 张不同的图。
**耗时提示**：一次调用是串行出图，总耗时 ≈ N × 单张（实测约 20~25 秒/张），6 张约 2~3 分钟。
不要依赖调高 AstrBot「工具调用超时」来出多张——本插件已内置「分批 + 后台续画」：单次调用最多连续出 4 张（draw_auto.max_images_per_batch，默认 4）并在 100 秒硬性时间兜底内收尾 return，剩余张数由后台任务自动补发，一次消息即可收齐 6/9/N 张，框架超时与否都不影响、也不卡死。保持 max_images_per_batch 默认 4 即可，请勿调太大（≥6 在慢服务器可能触发框架取消卡死）。
若插件提示「还差几张、请发消息续画」，照做即可（用户发新消息开新一轮继续画）。

- 用户没说数量时默认 1 张，不要自己补画第二张"换个姿势试试"。
- 对话记忆里以前说过的"多发几张"**只对当时那次有效**，不代表这次也要多发。
- 总张数受插件配置的单次上限约束（默认 3 张），超出会自动截断——照实传就行，
  插件会告诉你实际出了几张，你转告用户即可。

## 图生图判定：只认"本次消息里的参考图"

- 当且仅当**用户当前消息里真的附了图片**（或明确说"把这张图/参考这张图/这张照片变成XX"）时，才走图生图（把参考图交给插件，或传 image 参数）。
- **历史消息里的图、群聊里别人发的图、之前画过的图，都不算参考图。** 用户只是说"换个场景动作再来一张"这种延续旧图的请求，走**文生图**（重新 comfyui_draw 生成新图），不要试图去历史里找图当参考。
- 普通文字请求一律文生图。不要因为群里/上下文里出现过图就把请求当作图生图。

## 角色/作品的处理顺序（先角色 LoRA，没有再 danbooru）

当用户提到**具体角色/人物/作品/画风角色**（如「初音未来」「某个二次元角色」「绝区零的 Belle」）时，按以下顺序处理：

1. **先查角色 LoRA**：调 `comfyui_loras`（category 传「角色」或按角色名 keyword 搜）确认有没有匹配该角色的 LoRA。有就填进 `loras`，**不要**再用 danbooru 标签重复描述外形。
2. **没有匹配角色 LoRA 时**：才调用 danbooru MCP 查该角色/作品的标准标签。**这是查标签的唯一正确来源。**
   - **先看一遍自己的工具列表确认该 MCP 存在**：名字含 `danbooru` / `tag` / `标签` 的 MCP 工具都属于它（英文名或中文名都可能，如 `Danbooru tag search`、`Danbooru 标签搜索`、`danbooru_tag_search`、`search_danbooru_tags`）；**只调它**。
   - ⛔ **禁止联网搜索 / 抓取 danbooru 官网或镜像站**：官网会限流 / 403、网页格式也易错。你不应去「danbooru 源网站搜索」——即使你觉得 MCP 没生效，也不要用网页抓取替代。
   - **只取「角色专有 tag + 作品 tag」**：角色 tag 通常带作品名括号，如 `belle \(zenless zone zero\)`、`hatsune_miku`；作品 tag 如 `zenless_zone_zero`。**不要把搜索结果里附带的通用外观 tag 一起填进去**。
   - **括号必须写成 CLIP 安全形式**：danbooru 标签里的 `(` `)` 在 ComfyUI/CLIP 提示词里是「注意力权重」符号（如 `(cat:1.2)`），必须写成反斜杠转义 `\(` `\)`，否则标签会被拆坏、权重大乱。即 `belle (zenless zone zero)` → 写进 prompt 时变成 `belle \(zenless zone zero\)`。MCP 返回什么就照抄什么，不要自行增删括号。
   - 把「角色 tag + 作品 tag」填进 `prompt` 即可，**不要额外加外形描述**。
3. **默认绝对不改角色外观（重点中的重点！）**：角色 tag + 作品 tag 已锁定角色**完整**外观设定。**禁止**再叠加任何外观标签：
   - 发色 / 发型（`white_hair`、`blue_hair`、`long_hair`、`blonde`、`twintails`…）
   - 瞳色（`blue_eyes`、`red_eyes`…）
   - 耳朵 / 角 / 尾巴 / 兽化特征（`cat_ears`、`horns`、`elf_ears`、`tail`…）
   - 服装 / 配饰 / 体型（`white_dress`…）
   - **★ 你凭记忆写的角色外貌几乎一定是错的。** 真实案例：某个角色明明是**绿发**，模型却自作主张补了 `white_hair`，直接把角色画错。有角色 tag 时**你的记忆一律不作为依据**——拿不准就什么都不要写，**宁缺毋滥**；写错的外观标签比不写有害得多。
   - 只有用户**额外明确要求改某外观**（如「把头发染成粉色」「换成红裙子」「戴个墨镜」）时，才追加**那一项**对应外观标签。
   - ✅ **但「不补外观」不等于「写得干瘪」**：镜头（`close-up` / `upper_body` / `full_body` / `from_above` / `from_behind`）、光影（`backlighting` / `rim_light` / `cinematic_lighting`）、氛围与天气、场景环境、材质细节这些**非外观维度**照常写足（见「细节密度」）。这既让画面精致、又不会动到角色特征。
   - ⚙️ **插件侧已强制校验**：命中角色卡时，与锚点冲突的外观标签会被自动剥掉（白写），别赌。
4. 既无角色 LoRA 也无 danbooru MCP 时（**确认工具列表里确实没有该 MCP**），才退而用你自己的知识写**角色/作品 tag**（仍不要补外观）；**没有具体角色、只是泛化人物**（如「画个少女」「来只猫娘」）时，外观由你定，正常按需写发色/服装等标签。

## LoRA 怎么用（别再让用户给"确切名字"）

- 用户说"用 XX 的 lora""用那个鲸鱼娘 lora"这类话时：
  1. 先调 `comfyui_loras` 查询可用列表（可按底模过滤、按名称/关键字模糊搜）。
  2. 从结果里按名称/关键字匹配出确切名称，填进 `loras` 参数（如 `["ds_whale"]`）。
  3. 查不到/匹配不上就如实说"没有找到对应 LoRA"，不要编造名字。
- 用户给了名字但不确定是否准确，也可以先查 comfyui_loras 确认后填。
- 用户没提 LoRA → `loras` 参数不传，插件用配置默认。
- 用户提到**具体角色**时走上面的「角色/作品的处理顺序」：先查角色 LoRA，没有再调 danbooru MCP。

### ★★ 写提示词前先看「本次要用的」LoRA 描述（v7.7.74）

LoRA 库里的 `描述` 字段往往就是角色设定本身（"红发双丸子头金铃、灰渐变双马尾、红瞳、黑无肩带裙"），
**比凭记忆写外形准得多**。但要守两条：

1. **只查、只参考本次真正要用到的那几个 LoRA**：用 `comfyui_loras` 的 `keyword` 搜角色名/风格名，
   或按 `base_model` 过滤。**不要把整个库的描述都读进来**——库里有几十条，全读既挤占上下文，
   又会把**无关角色的特征带进画面**（这一步是多人同脸/串味的常见来源）。
2. **画面要与这些描述里的关键特征一致**（发色、发型、瞳色、兽耳、标志性服饰）。
   若这次要画的角色有 LoRA 但你**没有查它的描述**，就别凭记忆补外形——只写触发词即可
   （写错的外形比不写有害；插件也会剥除与权威锚点冲突的复述）。

> ⚙️ 插件内部整理提示词时（`/画` 指令、第三方插件调用等路径）会自动把「本次生效的 LoRA +
> 触发词 + 描述」喂给整理用的 LLM；你走工具调用路径时按上面两条自己查。

## 工作流怎么填（同上原则）

- **默认不传 `workflow` / `img2img_workflow`**（插件用默认工作流）。
- 只有用户明确要特定画风（真人/写实/动漫/二次元/某名字）时，先调 `comfyui_workflows` 查真实列表，按名称语义匹配后再填。
- 禁止凭记忆猜工作流名；拿不准就宁可留空用默认，也不要瞎填。
- 图生图时若列表里有名字含「图生图」的工作流，优先选它。

## 画多人 / 多人场景（计数标签 + 每个角色分组，避免「融脸/特征混在一起」）

当用户要画**两个及以上人物**（"两个女孩""XX 和 YY 一起""合照""一群人""大家都在""1男1女""姐妹""情侣"等），提示词写法跟单人完全不同，**必须显式声明人数 + 给每个角色独立分组描述**，否则模型极易默认画单人、或把几个人特征糊成一张脸（特征融合 / 多手多脚畸形）。

### 1. 先用「计数标签」声明总人数是第 1 位的

- 动漫（英文标签，Anima）：`1girl` / `2girls` / `3girls` / `multiple girls` / `1boy` / `2boys` / `1boy 1girl` / `1girl 1boy` / `group` / `crowd`。
  例：`2girls`、`1boy 1girl`、`3girls`。**放在提示词主体最前面（画质前缀之后）**。
- 真人（中文）：开头写「两个女孩」「一男一女」「三个人」，再分述各自特征。
- 注意：`solo` 是「单人」标签，**多人绝对不要写 `solo`**，否则和计数标签冲突、模型会只画一个。

> 不写计数标签，模型大概率只画 1 个人；写错人数（要 2 个却写 `1girl`）会直接少人。

### 2. 每个角色用「括号分组」独立描述，互不串味

用 `(角色描述:权重)` 把**每个人**的外观/服装/动作圈成一组，权重 1.1~1.3 让模型把特征绑定到对应个体、不互相污染：

> ⚠️ **动漫（Anima）模式括号里必须写英文标签**：动漫工作流会把含中文的片段交给 danbooru/LLM 翻译，翻译后 `(xxx:1.2)` 的权重括号会被丢掉、分组失效。所以动漫多人请全程英文标签（`(blue_hair, long_hair:1.2)`）；真人（中文/自然语言）括号内中英文都行（真人调用不翻译，括号权重语法直接生效）。

- 动漫（英文）：
  `2girls, (blue_hair, long_hair, white_dress:1.2), (red_hair, twin_tails, casual_clothes:1.2)`
- 真人（中文）：
  `两个女孩，(左边短发穿卫衣的:1.2)，(右边长发穿连衣裙的:1.2)`

具体角色（如初音未来、某 IP）按上面的「角色/作品的处理顺序」走——有角色 LoRA 就填 loras，没有就用 danbooru 角色 tag（带作品括号反斜杠转义），**每个角色各写一份分组**，不要共用一份描述。

> ★ **某角色用了角色 LoRA，触发词必须放进它自己的括号里。** 多人时若触发词不进分组、被全局追加到整段 prompt 末尾，两个角色的特征会互相串到对方身上、融角色。把该 LoRA 的触发词写进对应角色的括号分组（如 `(charA:1.2)`）；插件在多角色模式下也**不会**把角色 LoRA 的触发词全局追加（v5.14.0 起），未进分组的触发词等于没生效。触发词从 `comfyui_loras` 查询结果的「触发词」字段拿（查 LoRA 时一并取）。
>
> ★★★ **角色 LoRA 自带完整形象（外形 + 原服装），提示词里不要复述它。**
> **分组里只写「本图的变化项」**：该角色 LoRA 触发词 + 用户明说的东西（换的衣服、动作、表情）+ 场景/镜头。
> **禁止**再补发色 / 发型 / 瞳色 / 兽耳 / 角 / 体型——那是 LoRA 已经训练进去的东西，用弱文本标签复述会**稀释甚至覆盖**LoRA 的形象，而且你凭记忆写大概率写错。
> **服装同理**：用户没提穿什么时也**不要自己给两个角色编衣服**（实测 LLM 常给两人编同一套 `black strapless dress` + `detached sleeves`，标签系底模直接理解成双胞胎 → 两人同脸）。要换装就把用户说的那件写进该角色的分组。
> - ✅ 正确：`2girls, (suomingwuwa:1.25), (xinyuehu:1.25), holding hands, night, moonlit pavilion`（用户只说"画她俩"）
> - ✅ 用户说"给她换成红裙"→ `2girls, (suomingwuwa, red dress:1.25), (xinyuehu:1.25), …`（只给该角色加衣服）
> - ❌ 错误：`2girls, (suomingwuwa, red hair, twin hair buns, red eyes, black strapless dress:1.25), …`（复述形象 = 稀释 LoRA + 易撞脸）
> - ⚙️ 插件已做兜底：命中角色 LoRA 且用户本轮**没说**改外形 / 换装时，会自动剥除提示词里复述的**外形与服装配饰**标签（日志 `【LoRA 形象】`）；用户说了哪一项就保留那一项。
>
> ★★ **两个角色 LoRA 是同时、全局作用于整张图的**（LoRA 不认 prompt 分组，权重分组只是辅助）。所以真正能拉开两人的是**差异化的变化项**，不是复述形象：让两人穿**不同的衣服**（这条最有效）、做**不同的动作**、各有**不同的道具**。实测两人共写同一套 `black strapless dress` → 标签系底模把这理解成双胞胎，两张脸直接画成同一张（插件会就"分组共有标签"打 `【多人撞脸】` 告警，但换哪件衣服得听用户的）。要彻底避免串染需要 Regional Prompter 类区域控制（本插件暂未支持），或分开生成再合成。

#### ★★ 参考实现口径（v7.7.71 起按 Anima 参考实现架构执行，别再自行发明）

> 📌 **来源说明**：`anima-master` 是**第三方 AstrBot 插件**（用 Anima 模型做图的社区实现），
> **不是 Anima 官方仓库**。下面这条结论以及"混合式 / 身份锚点 / 不用角色 LoRA"都是**该参考插件的
> 方案选择**，不是官方规范；模型层面的权威依据只有 Anima 模型发布方（circlestone-labs）模型卡。
> 另外：**模型卡从未提过多角色 LoRA 同开**，所以"多角色 LoRA 不能用"是参考插件的取舍，
> 不是模型限制——你若想用角色 LoRA，插件也不拦你。

Anima 参考插件（源码在 `_Refs/anima-master`）对多人的参考插件结论是——**「第一版不提供每角色独立 LoRA、区域遮罩或 Regional Prompting。角色相似…仍可能需要多生成几个种子筛选」**（`docs/prompting.md:57`）。也就是说：

- **多角色 LoRA 同开是参考不支持的场景**，两人同脸不是提示词写得不好，是模型层面的限制；
- 参考保证身份一致性的手段**不是 LoRA，而是"角色名 + 权威标准 tag"**：LLM 给角色 tag 候选 → 插件查 Danbooru 校正 → 冲突的外貌直接丢弃（`docs/prompting.md:7`、`:49`）；
- 参考实现的最终提示词是**混合式**：`2girls, duo, holding hands, <公共tag…>` + `green-eyed girl: green eyes, dark school uniform, …`（每人一个**自然语言块**，见 `anima/prompts/multi_person_prompt.py:386` 与 `tests/test_multi_person_prompt.py:273-294`），**不用 CLIP 权重括号绑定身份**（参考只给"易混淆身份锚点"加 `(tag:1.3)`）；
- 参考多人负面词：`twins, duplicate characters, cloned character, extra person, fused characters, merged bodies, character sheet, multiple views, split screen, comic panels`。

> ⚙️ 插件已按此实现：出图链路会 ① 剥掉模型编造的外形/服装 ② 按**角色卡锚点 → Danbooru 校正**的顺序取权威身份锚点 ③ 把提示词改写成参考混合式。日志 `【身份锚点】` / `【多人混合式】`。
> ★ 所以**你不需要再自己写这些角色的外形**——写了会被剥掉，然后由插件用权威 tag 补上。
> ★★ 但**权威锚点拿不到时插件无法凭空发明**（原创 / 冷门角色 Danbooru 查不到）。这时最有效的动作是
> **把角色存进角色卡**（等价参考 `fixed_characters`）：用 `comfyui_character` 或角色指令把该角色的
> 标准 tag 存一次（例：`锁暝 = 1girl, red hair, twin hair buns, red eyes, black coat`），
> 之后每次画这个角色都会自动带上权威锚点。
> ★★★ 参考插件建议多人**多出几个种子筛选**（角色相似是已知现象）。一次调用里用 `prompts` 传 2~3 条
> 同一画面的不同变体比在提示词上纠缠更有效——但这属于用户主动要求，**不要擅自加张数**。

### 3. 角色之间的互动 / 构图（让画面真的"在一起"）

在计数标签和分组之后，补互动 / 站位词，避免各画各的飘在画面两端：

- 互动：**优先写「带部位」的接触词**——`cheek_to_cheek`、`head_on_shoulder`、`leaning_on_shoulder`、`hugging_from_behind`、`shoulder_to_shoulder`、`arms_around`。
- ⚠️ **别写笼统的接触词**：`hugging`、`holding_hands`、`leaning_on_each_other`、`arm_in_arm`、`embrace`、`kissing` 这类"没有具体部位"的写法，两人贴在一起时最容易糊成连体（实测高频）。
- 站位 / 构图：`side_by_side`、`standing_close`、`group_photo`、`from_side`、`sitting_together`、`back_to_back`。
- ⚠️ 纯提示词对「谁在左/谁在右」只是**软约束**，不能精确摆位。Anima 普通生图是单 positive 通道、没有 Regional Prompter，靠「计数标签 + 每角色分组」已是当前最佳近似；要精确构图得靠 ControlNet / 参考图（图生图）。

#### ★ 两人贴在一起时的「连体」防线（用户实测高频，必须遵守）

用户要的往往就是**贴在一起**（拥抱 / 贴脸 / 搭肩）——这没问题，**不要为了"分开"把构图改远**。要防的是「一个角色长出两个头」「A 的身体长在 B 的身上」这种融合畸形。三条硬规则：

1. **禁止把画面裁到腰线以上**：贴在一起时**不要**用 `close-up`、`upper_body`、`bust_shot`（"大头贴"）。腰线以下被砍掉后，模型会省掉躯干连接，两人下半身直接叠成一块——这正是"身体长在另一个身上"的最主要来源。**用 `cowboy shot`（保腰）或 `full_body`。**
2. **负向提示词必须带畸形抑制词**（可直接抄）：
   `conjoined, fused bodies, merged bodies, shared limbs, conjoined twins, two heads, extra head, multiple heads, extra torso, extra arms, extra legs, fused fingers, fused hands, extra fingers, bad anatomy, malformed limbs, poorly drawn hands, overlapping bodies`
   > ⚙️ 插件已做兜底：出图链路检测到多人（`2girls` / `1girl 1boy` / 中文「两个女孩」「合照」等）时，会把这串词**自动并入负向**（只增不覆盖，不会动你写的负向）。你仍可自己写，写了不会重复加。
   > ⛔ **负向里绝不要出现 `solo` / `1girl` / `2girls`**——那是抑制人数的，会把 2 人压回 1 人或干脆畸形。
3. **两人同时用角色 LoRA 时更要守住 1、2 条**：LoRA 是全局作用于整张图、不认 prompt 分组，两张脸压在重叠区域上，融合概率显著上升。

> 原理说清：`(角色A:1.2), (角色B:1.2)` 这种权重分组只做**注意力加权**，不做**空间隔离**。像素上重叠的两人，注意力区域也重叠，特征必然互串。所以贴得越近越容易糊——**贴一起也能做，靠的是负向畸形词 + 不裁太狠 + 带部位的姿势词**，而不是把人拉开。真要根治需要区域控制（Regional Prompter / 蒙版分区域）或分开生成再合成，本插件暂未支持。

### 4. 多人时的避坑

- ❌ 不写人数计数标签（默认画单人）。
- ❌ 只写"两个女孩"却不分角色描述（特征融合成一张脸、或两人长得一模一样分不清）。
- ❌ 把两个角色的外观标签平铺混在一起（如 `blue_hair red_hair`，模型不知道谁蓝发谁红发）→ 必须分组 `(蓝发:1.2), (红发:1.2)`。
- ❌ 动漫工作流用中文写人数（"两个女孩"）→ 必须用 `2girls` 英文计数标签。
- ❌ **多人提示词里出现 `1girl` / `1boy` / `solo`** —— 与 `2girls` 直接打架，模型可能只画一个或画三个；也包括把它们写进自然语言句子里（`1girl standing on the left and 1girl standing on the right`）。左右站位用 `side_by_side` / `from_side` 表达，或干脆不写。
- ❌ **prompt 里的角色触发词与 `loras` 参数对不上**（例如 loras 传的是 A、B，prompt 分组里却写着上一轮对话里的 C、D）→ 等于"加载 A 的模型、点名 C"，出图根本不是那两个人。传 `loras` 时必须同步把各角色触发词写进对应分组。
- ❌★★★ **把"各自的体型 / 服饰 / 动作 / 表情"写到括号分组外面**（实测高频，用户原话明明说了"她们各自有不同的体型服饰和动作"，模型却把 `petite, tall, black dress, red dress, sitting, standing, blush, smile` 全丢在公共区）→ **公共区的标签模型理解成两人共有**，于是两人穿同一套衣服、做同一个动作，直接同脸。
  ✅ 正确写法：**每个角色的体型/服饰/动作/表情一律写进该角色自己的括号分组里**；公共区只允许「人数计数 / 关系（side_by_side、holding hands）/ 场景 / 镜头 / 光影 / 氛围」。
  ```
  ❌ 2girls, (A:1.2), (B:1.2), petite, tall, black dress, red dress, sitting, standing, blush
  ✅ 2girls, (A, black dress, sitting:1.2), (B, red dress, standing:1.2), side_by_side, night, full body
  ```
  > ⚙️ 插件兜底：用户本轮说了"各自/分别/不同"等差异化要求时，出图链路会把公共区里的角色专属标签（服饰/体型/发色/动作/表情）**按顺序轮流归位**到各角色块（日志 `【多人混合式】… 归位`）。但轮流归位只是兜底，**顺序可能与你的意图相反**，所以还是请直接写进各自分组。
- ⛔ 标签系底模（Anima / Illustrious / Pony）里不要写自然语言句子（`two girls standing on the left…`）：CLIP 只当噪音 token，人数与站位都用标签表达。
- ❌ **角色 LoRA 已经给了完整形象，还把发色/发型/瞳色/兽耳写进分组** → 稀释 LoRA、且两人写得越像越撞脸；只写触发词 + 用户明说的变化项。
- ❌ **两个角色写同一套衣服**（`2girls, (A, black strapless dress:1.2), (B, black strapless dress:1.2)`）→ 标签系底模理解成双胞胎，两人画成同一张脸；至少让一位换衣服 / 换动作 / 加道具。
- ❌ **两人贴在一起还用 `close-up` / `upper_body`** → 裁掉腰线以下，必连体（见上节防线）。
- ❌ **写 `hugging` 这种笼统接触词** → 改 `cheek_to_cheek` / `head_on_shoulder` 等带部位写法。
- ✅ 画质前缀照常加（动漫 `masterpiece, best quality…`、真人 `最高画质…`），多人不影响前缀规则。
- ✅ 分组权重 1.1~1.3 即可，**别超过 1.5**（过高人物易过拟合/崩坏、且可能把该角色画得过重挤压别人）。

### 5. 示例

- "画两个女孩并肩站着" → 动漫 `prompt="masterpiece, best quality…, 2girls, side_by_side, (blue_hair, long_hair:1.2), (pink_hair, short_hair:1.2)"`。
- "初音和她的妹妹一起，两人各带角色 LoRA" → 先 `comfyui_loras` 查两人 LoRA + 各自触发词（如 `miku` / `imouto`），`loras=["初音LoRA", "妹妹LoRA"]`，`prompt="masterpiece…, 2girls, group_photo, (miku, blue_hair, twin_tails:1.2), (imouto, pink_hair, short_hair:1.2)"`（**两 LoRA 的触发词各自写进对应角色括号**，插件检测到已存在就不再全局追加，不会串味）。
- "一男一女在樱花树下" → 真人中文 `prompt="最高画质…, 一男一女, 樱花树下, (左边年轻男子黑发:1.2), (右边少女白裙:1.2)"`。

## 提示词语言

| 工作流类型 | 判断标志 | 提示词语言 |
| --- | --- | --- |
| 真人 / 写实 | 非 Anima | **首选中文**；用户明确要英文才用英文 |
| 动漫 / 二次元 | Anima | **必须英文标签**（如 `1girl, solo, white dress, beach, backlight`），开头固定加「画质前缀」（见下节），禁止中文 |

- 不确定类型时不传 workflow 用默认，并按默认工作流的类型写（通常真人→中文）。
- 负向提示词同样遵循语言规则。
- **动漫标签翻译（重要）**：当需要把中文动漫/二次元描述改写为英文 Danbooru 标签时，只要工具列表里有 danbooru MCP（名含 `danbooru` / `tag` / `标签`），**务必优先调用它**查询/确认标准标签（唯一正确来源），不要仅凭记忆臆造、也不要原样透传中文。⛔**禁止联网抓取 danbooru 官网 / 镜像查标签**。确认没有该 MCP 工具时才用你自己的翻译能力改写。**涉及具体角色时先走上面的「角色/作品的处理顺序」**，并且只写角色/作品 tag、不再补任何外观标签。
  - **查到的标签若含括号，填进 prompt 前必须写成 CLIP 安全形式**：`belle (zenless zone zero)` → `belle \(zenless zone zero\)`，因为 CLIP 把 `(` `)` 当注意力权重符号，不转义会拆坏标签、权重大乱。（插件对 anima 工作流会做一次兜底转义，但你不要依赖它。）MCP 返回什么就照抄什么。

## 画质前缀（v7.6.0 起由插件自动加，你不用写）

> ⚙️ **插件已接管**：现在画质前缀由插件按**底模风格自动补**（标签系 `masterpiece, best quality, very aesthetic, absurdres`；pony 系 `score_9, score_8_up, score_7_up`；NAI 平台 `best quality, very aesthetic, absurdres`；**自然语言系 flux/qwen/z-image/krea2 一律不加**——加了会被当成"要画出来的文字"渲染到图上）。
> 所以你**不需要**再手写画质词；写了插件也不会重复加。管理员可在「提示词丰富化」配置里改成分档/自定义。

## 细节密度（默认写丰富，别只丢一句主体）

除了外观维度（角色/作品 tag 已锁定的部分，见上节），**其余维度都该写足**，至少覆盖 6 个：

1. 主体与人数（含 `1girl` / `2girls` 计数标签）
2. 表情与动作（`smile` / `sitting` / `holding_cup`）
3. 构图与镜头（`close-up` / `upper_body` / `full_body` / `from_above` / `from_behind`）
4. 场景与环境（`indoors` / `classroom` / `rainy` / `night`）
5. 光影与氛围（`backlighting` / `rim_light` / `cinematic_lighting` / `sunset`）
6. 材质与细节（`detailed_background` / `intricate_details` / `wet_clothes`）

- 标签系底模：**15~25 个 Danbooru 标签**（不含画质前缀），每个都必须是真实存在的 danbooru 标签。
- 自然语言系底模：1~3 句整句，写清「主体 + 动作 + 环境 + 镜头 + 光影」。
- ⛔ 别为了「写丰富」去补角色外观——镜头光影写满、发色瞳色一个字都别动。
- ★ **命中角色 LoRA 或角色 tag（`name (work)`）时，上面第 1~5 条里的「人物外形」整条跳过**：
  LoRA / 角色 tag 已含完整形象（发色/发型/瞳色/兽耳/体型/原服装），提示词只需写
  **本图的变化项**（用户明说的衣服、动作、表情）与场景/镜头/光影。此时标签数可以少于 15~25，
  **宁少勿凑**——凑数只会把 LoRA 的形象稀释掉。

## 完整出图流程

1. **判意图**：新图 → 本技能；旧图/收藏图 → comfyui_gallery；用户明确"不要图/取消" → 不画，文字回应。
2. **判数量 + 判画面**：默认 1 张；要 N 张（无论几个画面）→ `prompts` 传 N 条不同画面；
   "各来 X 张" → 每组拆成 X 条、总条数 = 组数 × X。全部在**一次调用**里传完，不要拆成多次。
3. **判图生图**：本次消息带参考图才走图生图；否则文生图。
4. **需要指定则查询**：用户提 LoRA → comfyui_loras；提画风/工作流 → comfyui_workflows。没提就跳过。
5. **拼 prompt**：按语言规范写，主体/姿势/镜头/光影/场景/材质都写足（见「细节密度」）；画质前缀插件会自动加，不用你写。
6. **调用出图**：comfyui_draw（文生图）或 comfyui_img2img（本次消息有参考图）。prompt 必填。
7. **收尾**：把图交给用户，一句话结束。不要再补画、不追问"还要不要别的"。
   - **不要描述自己刚才做了哪些操作步骤**（「我先查了一下 LoRA / 又看了工作流 / 确认了底模，然后才画的」）。
     图片此时**已经发到群里了**，这种「找 XX、查 XX」的步骤播报放到图之后说，用户看到的就是
     "图都出来了你还在念查找过程"，时序完全颠倒。
   - 真想播报步骤，请在**调用出图工具之前**的那条消息里简短说一句（如「我去看看有哪些 LoRA 可用～」），
     然后直接调用工具，不要重复第二遍。
   - 收尾那句话只聊画面本身（caption 那种轻松口吻），别提 LoRA / 模型 / 工作流 / seed 等技术细节。
   **若出图失败、或被告知「本轮已经出过图了 / 没有产生新的图片」：如实告诉用户
   「这次没能画出来，稍后再试」，直接结束。绝对不要转去 comfyui_gallery 翻旧图顶替
   —— 用户要的是新画的图，用库存旧图冒充比直接说失败更糟。**

## 群聊 / 被动场景

- 在群聊里被 @ 要图、或用户发了参考图，同样按上述流程立即调用工具，不要因为"群聊人多/怕打扰"就不画。
- 用户明确说"别发了/不用了"才停止。

## 示例

- "画只猫" → comfyui_draw，真人默认中文 `prompt="一只可爱的橘猫，坐在窗台上，午后的阳光"`，1 张。
- "用鲸鱼娘的lora画张海洋主题" → 先 comfyui_loras 找到鲸鱼娘 LoRA 的确切名，再 comfyui_draw `loras=["鲸鱼娘名"]`。
- "把这照片转成动漫风格"（本次消息附图）→ comfyui_img2img，参考图交给插件，prompt 英文标签。
- "换个场景和动作，再来一张"（没附图）→ comfyui_draw 重新生成新图，不要图生图。
- "画三张不同姿势的" → 一次调用，`prompts=[姿势A…, 姿势B…, 姿势C…]`（3 条不同画面，每条 1 张），**不要分 3 次调**。
- "白天、晚上、深夜各来两张" → 一次调用，`prompts=[白天1…, 白天2…, 晚上1…, 晚上2…, 深夜1…, 深夜2…]`（6 条，每条 1 张 = 6 张）。
- "图呢/卡住了" → 立即再调 comfyui_draw，别解释。

## 不要做什么

- ❌ 只口头承诺"我会画"而不调工具（铁律 0）。
- ❌ 出图失败/被拦回后，转去 `comfyui_gallery` 翻旧图发给用户顶替
  —— 如实说"这次没画出来，稍后再试"。旧图不是新图，冒充会让用户更困惑。
- ❌ 把一次请求拆成多次调用 comfyui_draw——要多个画面/多张就用 `prompts` 一次传完。
- ❌ 用「单条 prompt + count=N」表达要 N 张——那只会出同一个画面的 N 个近似副本，该用 `prompts` 传 N 条不同画面。
- ❌ 默认多画几张；用户没说数量就只出 1 张。
- ❌ 把历史/群聊里的图当图生图参考图。
- ❌ 让用户"给确切 lora 名字"——有 comfyui_loras 就自己查。
- ❌ 凭记忆填工作流名。
- ❌ 动漫工作流输出中文 prompt。
- ❌ 给 wf/lora/宽高/seed/denoise 传用户没要求的参数——能不传就不传，插件有默认。
