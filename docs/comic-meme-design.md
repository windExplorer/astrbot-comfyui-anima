# 表情包 / 漫画功能设计（comic-meme）

> 状态：设计已确认，**第一期（通用底座）实施中**。第二期（功能层）待第一期验证通过后实施。
> 关联工作流：`workflow/表情包.json`

---

## 1. 背景与目标

用户希望通过一句想法直接产出**带文字的表情包**，并希望同一套机制能扩展到 **N 格漫画**（格数不固定：2/3/4/5/6/7…）。

核心诉求：

- **直出**：输入想法 → 出成图，中间不需要手工拼接、不需要跑两次。
- **通用**：不能为"表情包"写死一套逻辑，因为漫画格数是任意的。
- **不改现有行为**：现有工作流的出图逻辑必须逐字不变。

---

## 2. 核心洞察

### 2.1 工作流是「单条、两阶段串联」

`workflow/表情包.json` 的两个阶段**在同一条工作流内串联**，一次 `/prompt` 提交即可跑完：

| 阶段 | 底模 | 关键节点 |
|---|---|---|
| **前半 · 生图** | `anima_turboV11.safetensors` | `21` UNETLoader → `18` KSampler(8步) → `19` VAEDecode |
| **后半 · 编辑加字** | `boogu-edit-turbo-dit-Q4_0.gguf` | `11` TextEncodeBooguEdit（`images.image_1` ← **`19`**）→ `8` KSampler(4步) → `6` VAEDecode → `2` 放大 → `3` SaveImageExtended |

**`19` 的输出直接连到 `11` 的 `images.image_1`**，因此不需要"提交两次 + 中间传图"。这是整个方案能简化的前提。

### 2.2 「几格」是提示词的事，不是节点的事

Boogu 能直接根据提示词生成多格漫画（已实测确认）。因此：

- **格数写在提示词文本里**，由 LLM 自行判断。
- 代码**不需要知道有几格**，也不需要为每个格子准备一个节点。
- 表情包（2 槽）与 N 格漫画（2 槽）结构上完全一致，区别只在第二个槽的 `desc` 和 `template`。

## 3. Boogu-Image-0.1 调研结论

### 3.1 模型身份

`boogu-edit-turbo` = **Boogu-Image-0.1-Edit-Turbo**，华为 Leibniz AI 实验室（联合港大/港科大等）出品，Apache-2.0，10B，技术报告 [arXiv:2607.13125](https://arxiv.org/abs/2607.13125)。

⚠️ **不是 Qwen-Image-Edit**。它只是借用了 FLUX.1 VAE + Qwen3-VL-8B 文本编码器，模型本身独立。

| 变体 | 任务 | 步数 | CFG |
|---|---|---|---|
| Base | 文生图 | 25~50 | 2.0~5.0 |
| Turbo | 文生图 | 4 | 1.0 |
| Edit | 图生图 | 25~50 | 2.0~5.0 |
| **Edit-Turbo**（本项目使用） | 图生图 | **4** | **1.0** |

**当前工作流参数正确**：`steps=4` / `cfg=1` / `1024×1024`。官方明确 Edit 系列"支持最高 2K，但 **1K 分辨率下生成更稳定**"。

### 3.2 能力（与本功能相关）

- ✍️ **精准文字编辑**：中英文替换/新增/删除字符，可适配字体、字重、颜色、版式
- 📝 **文字渲染**：海报、邮票、文档、界面、品牌规范、手写板
- 🎨 **风格化**：明确包含"动漫肖像"

### 3.3 已知局限（官方原文，直接决定设计决策）

| # | 官方局限 | 对本项目的影响 | 对策 |
|---|---|---|---|
| 02 | 图生图一致性**不够稳定**（主体/身份/布局保持） | "anima 出角色 → boogu 保持角色"正是其弱项 | 模板强制"保持人物表情构图完全不变" |
| 03 | **小字号**/密集排版易错字、缺字、布局漂移 | 字多 → 字小 → 崩 | 自适应气泡尺寸 + 换行 |
| 05 | FLUX.1 VAE 重建损失大，**小人脸小肢体**易出伪影 | 多格漫画每格人脸变小 | 底部文字加粗描边；格数软上限 |
| — | Edit **目前仅支持 1 张参考图像** | 多角色漫画受限 | 待实测（`images.image_2` 字段存在，可能支持多图） |

## 4. 架构设计

### 4.1 设计原则

> **不新增平行的"表情包子系统"，而是把「工作流」的表达能力从「单路注入」升级为「多槽位声明」。**

理由：

1. 表情包、N 格漫画、"生图+加水印"本质都是**一条工作流需要多处、语义不同的文本注入**。
2. 做成通用能力后，新增一种玩法 = 只改配置，Python 零改动。
3. 若新增平行子系统，提交/轮询/取图/队列/限额/图库归档/NSFW/统计/WebUI 这些基建要复制一份，两边行为会漂移（已有 WebUI 双通道同步改的教训）。

### 4.2 分层

```
┌─ 配置层（数据，非代码）────────────────────┐
│  boogu_node   boogu 指令节点（两段提示词直出，推荐）│
│  prompt_slots  槽位声明（key/node/field/模板，旧方式）│
│  style_guide   风格锁                        │
│  resolution_mode / lora_anchor               │
└──────────────────────────────────────────────┘
                    ↓ 描述
┌─ 底座（第一期 · 通用）─────────────────────┐
│  find_all_nodes_by_class()                   │
│  resolution_mode: single | all | none        │
│  prompt_slots 注入 + 分档模板渲染            │
└──────────────────────────────────────────────┘
                    ↑ 调用
┌─ 功能层（第二期）──────────────────────────┐
│  /表情包 指令     comfyui_comic LLM 工具     │
│  _build_comic_slots()  LLM 造词              │
└──────────────────────────────────────────────┘
```

### 4.3 两个提示词走两条路（关键设计）

| | 提示词 ①（角色/画面） | 提示词 ②（加字/漫画） |
|---|---|---|
| 走哪条路 | **复用现有 `positive` 全流程** | **新增的 `boogu_node`（指令节点）** |
| 写入节点 | `15`（anima 正向） | `11`（boogu 编辑指令） |
| 输入框名 | `text` | `prompt` |
| 享受的现有能力 | ✅ 翻译、LoRA 预设、触发词追加、负向提示词 | ➖ 不需要 |

> **注意**：提示词 ① **必须**走现有 `positive` 路径。早期方案曾考虑"传 `positive=""` 把节点 15 交给槽位"，会**导致 LoRA 触发词、常驻预设、中文翻译全部失效**（这些逻辑的前置条件都是 `positive` 非空），已否决。

---

> **新简化配置（推荐）**：直出表情包现在只需在 workflow 配置里填 `boogu_node`（boogu 编辑指令节点 ID，如 `11`）即可，插件会一次性让内部 LLM 生成「绘图提示词(节点 A) + boogu 自然语言加字指令(节点 B)」两段，无需再配 `prompt_slots` 的 bubble/bottom 变量清单。`prompt_slots` 仍保留作为兼容旧方式。

## 5. 数据结构：`prompt_slots`

```yaml
prompt_slots:
  - key: caption                    # 槽位名
    node: "11"                      # 目标节点 ID
    field: "prompt"                 # 输入框名（默认 text）
    vars: [bubble_text, bottom_text] # 模板变量
    template:
      prefix: "固定前缀（一致性锁）"
      blocks:                       # 每个变量一个可条件渲染的块
        - var: bubble_text
          max_chars: 20             # 超过只警告，不截断
          tiers:                    # 按字数自适应选档
            - max_chars: 4
              text: "…气泡约占画面宽度32%…单行…字号非常大…"
            - max_chars: 8
              text: "…气泡约占画面宽度40%…单行…字号大而醒目…"
            - max_chars: 14
              text: "…气泡约占画面宽度50%…两行…字号较大…"
            - max_chars: 20
              text: "…气泡约占画面宽度58%…两行…字号中等偏大…"
            - max_chars: 999
              text: "…气泡约占画面宽度64%…两行…字号中等，确保完整…"
        - var: bottom_text
          max_chars: 24
          tiers: [ … ]
      suffix: "固定后缀（风格锁 + 防错字）"
```

### 渲染规则

1. `prefix` + **仅当变量非空时的 block** + `suffix`
2. block 内按 `len(text)` 取**第一个满足 `max_chars` 的档位**；都不满足取最后一档
3. **所有变量都为空 → 整个槽位跳过注入**，保留工作流 JSON 原文（避免出现"空气泡"）
4. 兼容旧的扁平写法：block 直接给 `text` 字符串（无 `tiers`）
5. `max_chars` 越界**只记日志警告，不截断**（硬截断会毁掉用户文案）

## 6. 自适应档位表

原理：用「气泡占画面宽度百分比」这个量化指标约束字号 —— 气泡越宽、字越少，字自然就大；字多了气泡变大 + 换行，字号温和下降。

推导基准：1024 画布，中文字稳定渲染需 **单字 ≥ 画布宽度 4%（≈40px）**。

### 气泡

| 字数 | 气泡占画面宽度 | 行数 | 字号 |
|---|---|---|---|
| 1–4 | 32% | 单行 | 非常大，几乎充满气泡 |
| 5–8 | 40% | 单行 | 大而醒目 |
| 9–14 | 50% | **两行** | 较大 |
| 15–20 | 58% | 两行 | 中等偏大 |
| 21+ | 64% | 两行 | 中等，确保文字完整 |

### 底部

| 字数 | 位置 | 行数 | 字号 |
|---|---|---|---|
| 1–6 | 底部 1/6 | 单行 | 非常大 |
| 7–12 | 底部 1/6 | 单行 | 很大 |
| 13–18 | 底部 1/5 | 单行 | 大 |
| 19+ | 底部 1/4 | 两行 | 中等偏大 |

**用「换行」而非「缩字号」消化长文本** —— 16 字挤一行必然糊，分成两行就稳。

> 每档都必须带：**气泡不要遮挡人物的脸**（气泡变大后更易踩）。
> 这些百分比是针对 1024 画布的**起始值**，实测后可直接在配置里调。

## 7. 文案规范：气泡 vs 底部

| | 气泡文字 | 底部文字 |
|---|---|---|
| **叙事身份** | **角色**（第一人称，画面内） | **旁白**（第三人称，画面外） |
| 回答的问题 | 她**嘴上在说什么** | 这个画面**实际在演什么** |
| 语气 | 口语、带情绪 | 概括、标签化、像视频标题 |
| 视觉 | 深棕字，气泡内，尖角指向嘴 | 白字 + 粗深棕描边，底部居中 |

**梗的来源是两者的「反差」**：角色说得越冠冕堂皇，底部点破的真相越荒诞。

| 场景 | 气泡（台词） | 底部（真相/旁白） |
|---|---|---|
| 偷偷删学习资料 | 放心，我只是帮你优化一下 | 当程序员说「帮你优化」 |
| 上班摸鱼 | 我在认真核对数据 | 摸鱼中 |
| 生产环境挂了 | 问题不大 | 挂了的第 3 分钟 |

❌ 反面例子：气泡"这个文件夹没用吧" + 底部"帮你清理一下" —— 两者同义反复，没有信息差，梗就废了。

三种组合都合法：**只要气泡**（纯台词梗）/ **只要底部**（状态标签）/ **两者都有**（反差梗）。

## 8. 职责划分：LLM 写什么，插件写什么

| | 负责方 | 理由 |
|---|---|---|
| 画面标签（base） | **LLM** | 有对话上下文，懂用户的梗 |
| 气泡/底部文字 | **LLM** | 文案是创作 |
| 云朵气泡形状、字体、描边、可爱风格 | **插件模板** | 固定资产，不该每次重写 |
| 角色一致性锁、防错字约束 | **插件模板** | 针对 Boogu 局限的工程补偿 |

好处：调气泡样式只改配置，不影响 LLM 行为；改 LLM 措辞也不影响画面风格。

### 两条入口路径不同

| 入口 | 谁造词 | 说明 |
|---|---|---|
| `comfyui_comic` 工具 | **外层 LLM 直接给** | 插件不做二次 LLM 调用，省一轮且保留上下文 |
| `/表情包` 指令 | **插件内部 LLM** | 指令路径没有 agent 在中间 |

## 9. 已知坑与对策

### 坑 1：LoRA 锚点会被「随机猜错」（最危险）

`_find_injection_anchors()` 在本工作流下 `model_srcs = {10(boogu), 21(anima)}`，两个候选取 `next(iter(set))` → **哈希序决定，等于抛硬币**。一旦选中 `10`，LoRA 被插进 boogu 编辑阶段，结果崩坏且**不报错**。

✅ **对策**：显式配置 `lora_anchor: "21"` + `lora_clip: "13"`。
（`lora_clip` 是为防将来某个 LoRA 配了 `model_only=false` 时 clip 源回落成无 CLIP 输出的 `21`。）

### 坑 2：宽高只改了一个 latent

工作流有两个 `EmptyLatentImage`（`12` boogu、`17` anima），自动探测只返回第一个（按 JSON 键序是 `12`）。

✅ **对策**：`resolution_mode: all` → 两个 latent 同步。

### 坑 3：512 兜底（最隐蔽）

```python
w = _ratio_w if _ratio_w is not None else (width or int(wf.get("default_width", 512) or 512))
```

`default_width` 未配 → 兜底 **512** 并**无条件注入**，会把 1024² 悄悄压成 512²。

✅ **对策**：配 `default_width/height: 1024`；或 `resolution_mode: none` 彻底跳过注入。
⚠️ 该兜底属于现有逻辑，**不修改**（改了会影响依赖它的现工作流）。

### 坑 4：采样参数一刀切

`set_sampler_params()` 遍历**所有** sampler 设同一套值，anima 的 8 步会覆盖 boogu 的 4 步。

✅ **对策**：`steps_off: true` + `cfg_off: true` + `default_denoise: -1`，沿用 JSON 原值（无需改代码）。

### 坑 5：`@style_name` 残留

工作流节点 `15` 原提示词尾部有 `@style_name`，**插件无任何替换逻辑**（从别处导出时带过来的）。

✅ **对策**：本功能会整体覆盖节点 `15` 的文本，残留自然消失。
