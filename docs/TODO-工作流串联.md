## 1. 需求

把两个（或多个）基础工作流**串成一条流水线**，例如：

```
qwen2.5-int8-noscale（出图）  →  vosr2-api（扩散式放大）  →  输出（用后者）
```

- 前者负责出图，它的**图像输出**接到后者的**图像输入**；
- 输出节点用后者的；可推广到 A→B→C，甚至"模块化重组"（并行、只借中间产物等）。

## 2. 可行性：已用真实文件实测（内存拼装，零错误）

测试样本：`logs/qwen2.5-int8-noscale.json`（A，出图）+ `logs/vosr2-api.json`（B，放大）。

| 检查项 | 结果 |
| --- | --- |
| A 解析 | `t2i`；保存 `490`；**图像出口 = `['491',0]`**（VAEDecode）；底模 `qwen_image_2.1_int8_convrot.safetensors`；无内置放大链 |
| B 解析 | `kind=upscale`；图入口 `1`，其消费者 = `节点2.images`；倍率 `easy int.value=3`、种子 `节点2.seed=6666` |
| 拼装动作 | B 的 ID 全部加前缀重映射 → 删 A 的保存节点 → `节点2.images` 接 A 的 `['491',0]` → 删 B 的 `LoadImage` |
| 合并后解析 | **零错误**；`kind=t2i`；**输出 = B 的 SaveImageExtended**；底模仍取 A；正/负向、宽高、采样器都指向 A；**悬空连线 0** |
| 图流向 | `SaveImage(B_9) ← B_2(TESpeedVOSR2Image) ← A 的 VAEDecode` ✅ |

**结论**：合并产物是一张**普通工作流**，所以下游零改动——工作流页引用、底模关联、LoRA、
尺寸决策、出图卡片、图库归档、重解析那一整套全部复用。

## 3. 三个必须遵守的技术要点

1. **不能把 IMAGE 连线塞进 `LoadImage`**：`LoadImage.image` 是 widget（字符串文件名），
   只接受图片连线的是它的下游节点。正确做法是**删掉 B 的图入口节点、把它原来的消费者直接
   接到 A 的图像出口**——与仓库里 `workflow_builder.bypass_upscale()` 已在用的「删节点 + 改接
   消费者」是同一套手术。
2. **ID 必须重映射**：两张图都会用 `1`/`2`/`9`，A 还可能含子图风格 ID（如 `489:451`）。
   加前缀并同步重写所有连线即可（实测 0 悬空）；`_meta`/标题不影响执行。
3. **必须删掉 A 的保存节点**（以及 PreviewImage 之类），否则每次出图 ComfyUI 多写一份中间图，
   而插件只按 `output_node` 取 B 的输出 → A 那份成为 output 目录垃圾。顺带好处：中间图不落盘。

## 4. 已知缺口（唯一需要额外动的地方）

合并后 `roles["upscale"]` 变成 `None`——解析器识别放大链是**只认类名关键词**
（`upscalemodelloader` / `imageupscale`），VOSR2 的处理节点 `TESpeedVOSR2Image` 认不出来。后果：

- 卡片「放大 ×3 / 模型名」、图库的放大说明丢失；
- **运行时无法调倍率/种子**（只能沿用工作流里写死的值）；
- 没有「绕过放大」的注记。

两种补法（倾向 (b)）：

- **(a) 记配方**：入库时把 `roles.compose = {a_id, b_id, id 映射, 倍率节点, 种子节点}` 存下，
  运行时按配方写；
- **(b) 泛化解析器**：把「保存节点上游的**图处理链**」从关键词匹配改成**通用回溯**
  （从 save 沿 `images` 上溯到图像源之间、非透传的节点都算处理链），其中带 `scale`/`seed`
  可写字段的记为可调控件。这样任何自定义放大节点（VOSR2、SeedVR2…）都能被识别，
  **无论是否组装都受益**。

## 5. 产品落点（两条路线）

| | 方案 A：基础工作流页「组装工作流」（**推荐**） | 方案 B：「更多功能」里的"组合功能"（绑 A+B，运行时现拼） |
| --- | --- | --- |
| 做法 | 选 A + 选 B → **生成合并 JSON 走既有 `import_json` 入库**，并留 `roles.compose` 配方，支持「重新组装」 | 不落库，出图时现拼 |
| 优点 | 下游零改动；解析校验 / 详情节点表 / 删除引用检查 / 底模关联全部复用 | 不产生新记录；无「重新组装」概念 |
| 缺点 | 多一条记录；部件更新后需（一键）重新组装 | 绕过库的校验与展示；工作流页选不到它，不能作为普通工作流出图 |

## 6. 风险清单

- **显存**：两个模型同时驻留（A 的 UNET + B 的 VOSR2）；3× 放大在 8G 卡上可能吃紧，
  建议保留 B 自己的 tile/内存策略。
- **尺寸爆炸**：A 出 832×1216 再 ×3 = 2496×3648。建议组装时提示 + 可选的「输出长边上限」护栏。
- **双重放大**：A 自带内置放大链时再串 B 就是放大两次。建议**默认 bypass A 的内置放大链**
  （现成 `bypass_upscale` 即可），并给开关。
- **重解析会丢配方**：`reparse()` 只更新 `roles_json` → 需保留旧 roles 里的 `compose` 字段。
- **多阶段（A 有采样器 + B 也有采样器）**：合并后是两个采样器，而当前校验器硬性要求
  「恰好 1 个采样器」，会被拒。故 **v1 只支持 A 单采样器 + B 纯处理类**（`kind=upscale`，
  正好是上面的例子）；出图→重绘这类两段采样需放宽核心不变量并定义「步数/CFG 归哪一段」。

## 7. 分期建议

- **Phase 1（一个版本可出）**：`workflow_composer.py`（合并 + 严格校验 + 可读报错）+ 基础工作流页
  「组装工作流」弹窗（选 A/B、「绕过 A 的内置放大链」开关）+ 落库 + 详情页显示组成 +
  测试（用上面两份真实文件做端到端：合并后解析 0 错误 / 无悬空 / `save=B` / `model=A` / 注入点正确）。
- **Phase 1.5**：解析器泛化「保存上游的图处理链」（见 §4 (b)），让合并后仍能识别与调整放大模型/倍率。
- **Phase 2**：「重新组装」按钮、输出尺寸护栏、是否保留中间图的开关。
- **Phase 3（可选）**：A→B→C 多段；两段采样串接（需放宽「单采样器」不变量）；
  并行组合（同 prompt 两个工作流各出一张对比）需要新的「多输出节点」支持。

## 8. 与现有能力的关系（避免重复造轮子）

- 现有 `upscale_mode = inject` + `放大模型名`：能在出图工作流里插一套
  `UpscaleModelLoader + ImageUpscaleWithModel`（4x-UltraSharp / RealESRGAN 这类）。
  **「一个模型 + 一个节点」的放大不用组装，现有功能就够。**
- **VOSR2 / SeedVR2 这种「自带模型加载器 + 设置节点 + 倍率/种子」的扩散式放大**，
  `inject` 做不了（它只会插一个 upscale_model 节点）——**这正是串联功能的价值点**。
